# 开发工作流

## 构建约束

- 修改代码后，默认**不执行** `npm run build`、`next build` 或其他完整生产构建命令。
- 只有用户明确要求构建，或构建是定位当前问题唯一必要的检查且已向用户说明并获得同意时，才可以执行。
- 可根据当前改动选择更轻量的验证，例如定向测试、类型检查或 lint；不以“例行验证”为理由自动升级为完整构建。

## Git 提交规范

- 提交信息必须遵循 Conventional Commits：`type(scope): 简短中文描述`，其中 `scope` 可省略。
- 可用类型：`feat`（新功能）、`fix`（问题修复）、`refactor`（重构）、`docs`（文档）、`test`（测试）、`style`（不影响逻辑的样式）、`chore`（构建或杂项）。
- 标题使用中文、简洁说明改动目的；重要改动必须在空行后补充中文正文，以项目符号说明关键实现、兼容性影响和已执行的验证。
- 提交前仅暂存本次任务相关文件，并运行与改动匹配的轻量检查；不得以未验证的构建结果替代实际说明。
- 未经明确授权，不得修改他人提交或已推送提交；修正自身尚未推送的提交时，仍须完整遵循本规范。
